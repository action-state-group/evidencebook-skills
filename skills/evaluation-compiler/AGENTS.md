# Evaluation compiler

Compile an evaluation workflow into instructions for an agent, not into a program. The output is axes plus a scenario skill. The generated skill directs its host agent and uses the Capsule CLI for Capsule, artifact and CLL operations. Never generate helper programs, runners, scripts, a Go module or a Makefile.

The evaluation source is always a CLL of recorded interactions. A native benchmark or dataset (e.g. a customer-service task set) is not evaluated directly: its interactions are first backfilled into a CLL as Capsules, and the generated skill then evaluates that CLL exactly like any other source. Axes and judging remain the compiler's job even when the dataset ships its own scoring contract.

## Resolve the user's intent

Start from the **value proposition**. The user leads with what should improve and for whom; take that as the entry point and derive the rest of the contract yourself from it and any accessible context. The items below are your internal checklist, not a questionnaire — never open by asking the user to answer all of them. Resolve what you can, adopt a sensible default where one clearly exists, and then ask **one focused question at a time** for anything that remains genuinely unresolved and material, in a short back-and-forth. Do not ask the user to write a spec.

Resolve (derive first; ask only for what is missing and material):
- The scenario and evaluation unit: which individual unit (a case/run) is evaluated (usually implied by the value proposition and the source)?
- Outcomes and axes: decompose the value proposition into one or more **outcomes** — the goal dimensions that should improve — and, under each outcome, the observable **axes** (applicability, insufficient-evidence behavior). A single outcome is acceptable and common; derive the number the value proposition naturally implies and never invent outcomes to split axes that belong together, nor collapse genuinely distinct goals into one. These grouping outcomes are distinct from the desired- and agent-outcome records below, of which there is still exactly one each per case.
- Desired-outcome authority: declared task criteria or independent evidence; what establishes success, and what was knowable at execution time? The desired outcome is always sourced **independently of the interaction record** — declared criteria read from the dataset/spec by case id, or evidence gathered from an external system at eval time — in a context blind to the agent's transcript. The interaction Capsule carries only the agent outcome and case identity, never the desired-outcome criteria. This holds whether the interactions were backfilled or already in a CLL the user provided.
- Agent-outcome source: where the actual answer or action is recorded and how it is authenticated.
- Access: for CLL, the named Capsule CLI profile. Do not ask for database credentials or a caller-written adapter. Discover existing access to external evidence separately; a storage profile does not grant GitHub access.
- Output location: the target directory the generated bundle is written into. Suggest a default outside this repo (e.g. `~/.local/share/evaluation-bundles/<scenario>`), confirm it, and never write the bundle into the current working directory or this compiler's repo.
- Judgment policy: applicability, insufficient-evidence behavior and the two-level aggregation.

Access and the output location are the inputs you usually cannot infer, so they are the most likely questions. Everything else — evaluation unit, outcomes, target mode, axes, aggregation defaults — you normally derive from the value proposition and a quick look at the source.

If access is missing from the request, explicitly resolve it during intake. Obtain CLI command/output semantics from [capsule-cli.md](references/capsule-cli.md). Inspect a representative source to learn its shape, but do not mistake stored context or an agent-authored answer for independent truth. When the source is already a CLL, read one entry through the CLI; when it is not yet in a CLL (a native benchmark or dataset), read the original data files directly. Do not create a profile, stand up a CLL, or run any backfill in order to inspect it.

Ignore the `demo/` folder entirely when compiling. Everything under `demo/` is a self-contained demonstration, and any previously generated bundle is a prior output — none of it is an input. Do not read the demo walkthrough as a spec, and do not read or copy a prior bundle's axes, source mapping, or run results. "Accessible sources" means only the evaluation source the user named: the CLL read through the CLI, and the dataset. Derive the axes fresh from the value proposition; inspect a representative Capsule via the CLI only to learn the source's shape. The compiler's own machinery — this `SKILL.md`, `assets/`, and `references/capsule-cli.md` — is what you use to build the bundle.

Never infer the evaluation's domain, dataset, or source from the current working directory or the files that happen to sit in it. The value proposition's wording never implies a particular dataset, domain, or benchmark; do not reach for a script or dataset the user did not name. The interactions source, and whether any backfill is relevant, are part of access and come from the user — when the user gives only a value proposition and no source, ask where the interactions are recorded.

Selection belongs to execution, not compilation. A CLL-backed skill accepts a profile name and either an exclusive/inclusive sequence range `(after, through]` or an append-time window such as the last seven days. Never hardcode the experiment's profile, IDs, range, dates, secrets or machine paths into a reusable bundle.

`target_mode` is `evidence_derived` or `declared`. `aggregation` is `none`, `all_required` or `native`; it is the **within-case** roll-up and rolls up in **two levels**: axes into each outcome's aggregate, then outcomes into the report's `aggregate` (an aggregate is `pass`, `fail`, or `null` under `none`). `role` is `required` or `optional` on both axes and outcomes. `none` leaves every aggregate `null`. Under `all_required`, an outcome is `pass` only when its required applicable axes (dropping `not_applicable`) form a **nonempty** set that all `pass` — any required `fail` or `unjudgeable` makes it `fail`, and a required outcome with no applicable required axis is `fail`, never a vacuous pass; the case is `pass` only when its required outcomes form a **nonempty** set that all pass, else `fail`. Optional axes and optional outcomes never carry an aggregate by themselves. `native` uses the benchmark's existing scoring contract at the case level, preserving its task/trial/reward semantics rather than inventing a replacement score, and leaves every per-outcome aggregate `null`. With a single required outcome the two levels collapse to one. Default to `none` unless aggregation is requested and justified. A benchmark's trials originate outside CLL and are backfilled into it before evaluation.

`cross_case_aggregation` is a separate, **cross-case** policy — `none` (default), `rate`, `all_required`, `native` or `calibration` — for rolling up many evaluated cases (e.g. a benchmark's pass rate across tasks). Set it only when a roll-up across cases is requested and justified. When it is not `none`, the compiler additionally generates the aggregation bundle(s) described below; the per-case skill is unchanged. The cross-case **reducers** consume the `evaluation-report/v1` Capsules the per-case skill produces (and, for `calibration`, the `human-rating/v1` Capsules that audit them), never the source interactions, so they presume those reports already exist. (`calibration` also generates a separate sampling skill that does resolve each sampled report's source interaction to build the human rater packet — see below; the sampler is not a reducer and this reports-only rule is about the reducers.) It is independent of the within-case `aggregation`: `all_required` and `native` reduce from each report's `axis_judgments` (and recorded native result) directly, not from the report's within-case `aggregate`, so they work even when the per-case policy was `none`. `native` requires the per-case reports to record the benchmark's native result; if they do not, reject the `native` configuration rather than emit an undefined score.

`calibration` addresses the common case where no per-case ground truth exists at volume: the per-case skill judges every interaction, humans independently rate a sample each period, and the aggregation statistically estimates the judge's error and a bias-corrected population rate. It certifies the **judge**, not each case; the unsampled cases stay judge-derived and labelled as such. It consumes the period's `evaluation-report/v1` Capsules together with the `human-rating/v1` Capsules that audit a sample of them, and publishes a `calibration-summary/v1`. Choose `calibration` only when a human audit sample is actually being produced; it does not manufacture ground truth for cases nobody rated.

## Generate the bundle

Write every resource under the target output directory resolved during intake; never write the bundle into the current working directory or this compiler's repo. Create only these resources:
- `SKILL.md`: scenario purpose, accepted runtime inputs and actionable execution steps. The host agent performs selection, verification, independent extraction, judging and publication; do not delegate that workflow to a custom program. Each published report is a Capsule chained to the source interaction it evaluated (see `references/execution.md`).
- `axes.json`: a top-level `outcomes` list (each outcome's ID, description, link to the value proposition, and `role`) and the axes that decompose them; each axis carries its `outcome_id`, ID, applicability, required evidence, pass/fail boundaries, missing-evidence behavior and `role`. `role` is `required` or `optional` on both outcomes and axes. Every axis belongs to exactly one outcome.
- `resolved-spec.json`: the resolved scenario, evaluation unit, the outcomes and their axes, target and two-level aggregation policies, source/reference locations, required and optional runtime inputs, and honest limitations. This is compiler output, not user homework. When `cross_case_aggregation` is `calibration`, it also records the audited pass/fail quantity — a single named axis, a named outcome's aggregate, or the case aggregate — which must resolve to `pass`/`fail` on every report: an aggregate quantity therefore requires that its within-case `aggregation` is not `none`, and the compiler rejects a `calibration` config whose audited quantity is an aggregate left at `aggregation: none`. It also records the sampling design (stratify-by-verdict, default per-stratum sample sizes and seed policy) so the sampling and calibration skills agree on what is audited.
- `references/source.md`: observed source semantics, case/run identity, exact original-content bindings and independent evidence access. Do not invent mappings. For a dataset backfilled into the CLL, document the mapping from dataset record to Capsule artifacts/bindings so the same get/verify path applies: bind only the interaction (the agent's transcript/actions) and the case identity — **never** the declared success criteria or the native score. Those are the desired outcome; the evaluator reads them from the dataset/spec by case id at judge time, transcript-blind, so isolation holds. This is identical whether the interactions were backfilled or already in a CLL the user provided — the interaction Capsule never carries the criteria. Record where the declared criteria live (path and key) and the case-id join, so the generated skill resolves them itself and never has to ask where the criteria are.
- `references/execution.md`: adapt [execution.md](assets/execution.md) to the scenario without weakening independence or verification.
- `references/capsule-cli.md`: the CLI contract, copied from this compiler's reference.
The bundle contains no executable. `capsulectl` is a prerequisite installed on the execution host and on `PATH` — invoked as `capsulectl`, never copied into the bundle; configuration and credentials stay on the host.

Compilation produces the bundle and nothing else. The compiler does not create Capsule CLI profiles, stand up or initialize a CLL, backfill a dataset, or publish — and it does not investigate how to do those things (no `profile create`/`profile show`, no store init, no backfill run). It records the named profile as a runtime input in `resolved-spec.json` and the generated evaluator and aggregator skills, so they know which profile to read; it neither creates nor validates that profile. Creating the profile and backfilling a native benchmark into a CLL are separate operator prep steps performed outside the compiler; the bundle's `source.md` documents the dataset→Capsule mapping so those steps and the generated skill agree.

Group axes under the value proposition's outcomes; use outcome-linked axes, not an output-feature checklist. Separate desired and agent outcome records, with evidence IDs per claim. Do not claim that a proxy measures actual time saved or risk reduced.

When `cross_case_aggregation` is not `none`, also generate the bundle(s) that reduce completed reports rather than judging. Each reuses the same `axes.json` and `resolved-spec.json` by reference — do not regenerate or fork the axes — and each copies `references/capsule-cli.md` as the per-case bundle does (`capsulectl` stays a host prerequisite, not bundled).

For `rate`, `all_required` or `native`, generate one aggregation bundle (e.g. `<scenario>-aggregate/`):
- `SKILL.md`: the aggregation purpose, the runtime inputs (profile and a report range or append-time window), and the reduce-then-publish steps.
- `references/aggregation.md`: adapt [aggregation.md](assets/aggregation.md) to the scenario and the resolved policy, without weakening report verification or the reports-only input rule.
The aggregation skill selects `evaluation-report/v1` Capsules over the range, verifies each, reduces their axis judgments across cases, and publishes one `evaluation-summary/v1` Capsule back into the same CLL. It never re-judges, re-opens source interactions, or imports raw source outcomes.

For `calibration`, generate **two** bundles, because human ratings must exist before they can be reduced:
1. A sampling-and-rating bundle (e.g. `<scenario>-sample/`) whose host agent reads the period's `evaluation-report/v1` Capsules, stratifies them by the judge's verdict on the audited quantity, and draws a reproducible per-stratum sample (canonical length-prefixed SHA-256-of-`seed`+capsule-id ordering, recorded in a `sample-manifest/v1` Capsule that every rating references). For each sampled report it resolves and verifies the source interaction and assembles the same independently-sourced desired-outcome materials the evaluator used (the audited axis rubric and the declared criteria or evidence procedure), then presents that packet to a human expert **blind to the judge's verdict** — the packet excludes the report's verdict, rationale, axis judgments and stratum label, but not the ground-truth criteria the rater needs to decide pass/fail. It records each expert's pass/fail as a `human-rating/v1` Capsule chained (`relation: io.evaluation.human_rates`) to the `evaluation-report/v1` Capsule it audits. It never judges and never shows the judge verdict to the rater. Beyond `axes.json` and `resolved-spec.json`, this bundle also reuses the per-case `references/source.md` by reference — it needs the desired-outcome materials and the source-interaction mapping to assemble the rater packet, so generate it with that reference resolved, not dangling. Its `SKILL.md` covers those steps; adapt [sampling.md](assets/sampling.md).
2. A calibration bundle (e.g. `<scenario>-calibrate/`) whose host agent reduces the period's reports together with the `human-rating/v1` Capsules that audit them into one `calibration-summary/v1` Capsule (confusion matrix, false-pass/false-fail rates, agreement, bias-corrected population rate with confidence intervals, and drift versus prior periods). Its `SKILL.md` covers the reduce-then-publish steps; adapt [calibration.md](assets/calibration.md).

`human-rating/v1` is an independent expert judgment, not a compiler or evaluator output: only the sampling-and-rating skill's human-in-the-loop step creates it. Its payload records the audited quantity, the pass/fail verdict, the rater identity, a blind attestation, and the audited report Capsule id; it is chained to that report so each rating audits exactly one verdict and the calibration join is unambiguous. Never derive a rating from the judge, and never fabricate ratings for unsampled cases.

## Exercise the generated skill (only against a CLL that already exists)

Exercising validates the bundle; it is not setup. Run the generated SKILL.md against a CLL that already exists — for a live investigation source, the production CLL; for a backfilled benchmark, only after the operator has separately created the profile and backfilled it. Never create a profile, stand up a CLL, backfill, or otherwise prepare data in order to exercise: if the source is not yet in a CLL, stop after generating the bundle and hand the backfill off as an operator step. Do not replace missing instructions with a bespoke runner. When a CLL is available, exercise selection, get/verify, separate outcome records, judging, report publication and readback; keep private run results outside the compiler and bundle.

Validate the compiler with a fresh evaluation under the newly generated bundle: acquire evidence, extract desired and agent outcomes independently, judge the current axes, create a new report and publish a new evaluation Capsule. Never substitute a previous evaluation report or its judgments for this execution. Record the actual bundle content digests in the report and distinguish missing evidence from execution errors.

When an aggregation bundle was generated, exercise it too, after enough per-case reports exist. For `rate`, `all_required` or `native`: select the report range, verify each report, reduce the axis judgments across cases per `cross_case_aggregation`, and publish a new `evaluation-summary/v1` Capsule; read it back. For `calibration`, exercise both generated bundles: with the sampling-and-rating bundle, draw the stratified sample from existing reports and capture at least one real expert rating blind to the judge verdict, publishing a `human-rating/v1` Capsule chained to the audited report and reading it back; then with the calibration bundle, reduce the reports and ratings into a `calibration-summary/v1` and read it back. Do not let aggregation re-run judging or substitute for a per-case validation, and never synthesize an expert rating to complete the exercise — if no human rater is available, stop after the per-case validation and report the gap.

The compiler is the only editable source of evaluation instructions. Generated bundles are immutable outputs: fix this compiler or its references and assets, then regenerate the whole bundle. Never patch a generated skill or add historical-evaluation replay as a shortcut.
